# 大营销平台

## DDD构架设计

### 简化理解

在给大家讲解 MVC 架构的时候，小傅哥提到了一个简单的开发模型。开发代码可以理解为：`“定义属性 -> 创建方法 -> 调用展示”`但这个模型结构过于简单，不太适合运用了各类分布式技术栈以及更多逻辑的 DDD 架构。所以在 DDD 这里，我们把开发代码可以抽象为：`“触发 -> 函数 -> 连接”` 如图：

![img](./../大营销平台系统.assets/road-map-230624-02.png)

- DDD 架构常用于**微服务**场景，因此，系统的调用方式就不只是 HTTP 还包括；`RPC 远程`、`MQ 消息`、`TASK 任务`，因此这些种方式都可以理解为触发。
- 通过触发调用函数方法，我们这里可以把各个服务都当成一个函数方法来看。而函数方法通过连接，调用到其他的接口、数据库、缓存来完成函数逻辑。

### 策略概率装配处理

#### 业务诉求

总结：**抽检策略的存储和处理算法**，使用**Redis**存储范围值，用于解决分布式问题。

【空间换时间】总结：**本地内存更快，Redis可以解决分布式存储问题。**

【时间换空间】总结：**抽奖时生成一个随机值，和设计好的抽奖策略的概率范围比较**。【当**存储空间大**时使用】



从这一章节开始，小傅哥会带着大家正式进行需求的开发实现。我们会先梳理出业务流程，并不断的实现各个模块流程的功能。这包括本节要实现的**抽奖策略的装配**，这个过程中会需要用到数据库查询、策略值计算、Redis Map 数据存储。也会在这个过程中体现出 DDD 分层架构下的开发实现方式。

**注意**；关于抽奖算法知识。

抽奖的算法一种是**空间换时间**，另外一种是**时间换空间**。映射到方案上，空间换时间，是提前计算好抽奖概率分布，用本地内存 guava 或者 redis 存储，最后抽奖的时候通过生成的随机值，在空间内定位即可，复杂度为O(1)。

**本地内存更快**，Redis 相对慢一些。但 **Redis** 可以直接解决**分布式存储问题**，本地内存需要让多台分布式机器都保持数据的同步更新，需要引入配置中心以及定时检测的手段，来处理应用**启动前/运行中**，对活动**新增/变更**做本地内存做数据加载处理（大厂中一些非常高并发的场景，会申请内存更大的机器来做这样的事情）。

【空间换时间】总结：**本地内存更快，Redis可以解决分布式存储问题。**

另外一种是时间换空间，就是抽奖的计算，可以抽奖的时候生成一个随机值，之后和概率范围for循环比对。这样的场景适合那种需要，非常大的空间存放抽奖概率，不划算的时候，可以考虑这种。也可以在程序中设定，当总概率值超过100万，则不存储，而是改为循环比对。但，一切的手段，都要与实际诉求来依赖。

【时间换空间】总结：**抽奖时生成一个随机值，和设计好的抽奖策略的概率范围比较**。【当**存储空间大**时使用】

### 策略权重概率装配

总结：根据不同的**积分累计消耗【权重概率】**来设置**不同的奖品范围**

方法：初始化一个全装配（包含所有奖品）的数组，然后查询不同权重概率，获取对应的奖品范围，删除不在该范围内的奖品即可。

策略分类：

- 策略+ 无权重，默认策略执行
- 策略+ 权重，策略权重概率装配

#### 业务述求

在大营销平台的抽奖子模块中，需要满足用户抽奖N积分后，可中奖范围的设定。也就是说你总共消耗了6000积分抽奖了，那么接下来的抽奖就会有**圈定到固定的奖品范围**，不会让用户再抽到过低价值的奖品。那么这就需要我们在设计系统实现的时候，处理下不同策略规则权重的概率装配。

### 不超卖库存规则实现 

总结：使用**Redis**缓存奖品库存，解决超卖问题；使用**Redisson延迟队列 + 定时任务消费**，完成数据库内容更新。

【注意】：**首先对于库存集中扣减类的业务流程，是不能直接用数据库表抗的。**

方法：

- 库存消费：借助**Redis**，缓存奖品库存
- 数据库同步：库存消耗之后，更新库表内容：Redisson延迟队列 + 定时任务，缓慢消耗队列数据据来更新数据库表内容。

![img](./assets/FnjGpdxV5WZ88pMCciqIsTbbdL6h.png)

#### 业务

当通过抽奖策略计算完用户可获得的奖品ID后，接下来就需要对这一条奖品记录进行**库存**的扣减操作。只有奖品库存扣减成功，才可以获得奖品ID对应的奖品，否则将走到兜底奖品。

#### 具体步骤

库存扣减：

- 库存装配：首先访问数据库将库存缓存到Redis；

- 使用**decr**操作扣减库存（decr是原子操作）

  - 库存超卖问题：先尝试使用decr扣减库存，但扣减之后库存小于0，则重置Redis库存为0，并扣减失败。

  - 库存恢复/重买问题【数量从98->96,后面由于其他原因恢复到98，此时98已经卖出去了，不应该再被卖】：将`decr_数量值（如98)`作为一个key添加到Redis中，并使用**setnx**加锁；如果查询到该数值已经加过锁了，那么就不能再次消费；

- 扣减库存成功，则将该扣减动作加入到Redis的延迟队列；延迟固定/特定时间之后再写入队列中。
  - 延迟队列实现：使用Redis的延迟队列，并使用一个key标记该队列。

数据库同步：

- 定时任务（**Scheduled注解**）
  - 获取延迟队列内容
  - 队列存在内容则更新数据库库存

#### 业务述求

为用户的行为数据，使用路由组件将数据散列到分库分表中。

分库分表也是分布式架构中一个非常常用的数据存储方案，通常在公司中创建的系统都是直接创建出带有分库分表的系统架构。因为本身分库分表就是一个很成熟的方案，系统的分层和开发的熟练度都非常高。如果早期设计为单库单表的，那么后期再想扩展为分库分表则会有非常大的数据迁移和工程改造成本。

那么，分库分表以后，早期需要更多的数据库资源吗？其实并不用的，对于早期上线的系统，如果评估没那么大的体量，则可以使用虚拟机的方案安装数据库，也就是原来1台物理机，装1个数据库，现在则是2台物理机拆分为虚拟机，各个应用互相使用【作为主备】。而你占用的都是虚拟资源。也就是原来1台物理机等于5个虚拟机，现在5个虚拟机被分配到各个物理机上。所以你的分库分表并没有额外占用更多的资源。但这样的设计，业务体量上来以后，扩展只需要调整虚拟机的分配就可以了。

### 抽奖活动订单流程设计

总结：修改库表设计，区分不同行为（签到/支付/兑换等）导致的总、日、月次数变化，与抽奖活动表实现解耦。

修改原理：

- 调整前：活动库存=1000次，用户签到或支付都从这1000次扣减，无法区分行为。

- 调整后：

  - 抽奖活动表只负责抽奖活动的总体设计
  - SKU表负责抽奖次数，定义不同的行为获取不同次数，（签到获取1，转发获取 3次抽奖机会），并且拥有单独的库存
    - SKU1：签到奖励（库存99999，每次发1次抽奖）
      - 参与次数表：添加总次数、日次数、月次数均为1的数据
      - 活动sku表：添加代表签到的skuId、活动id、签到对应的次数编号、签到对应的单独库存总量与剩余库存。
    - SKU2：支付奖励（库存5000，每次发3次抽奖）

  - 抽奖活动表如同货架， SKU表则是该货架的商品，用户只需要购买商品，而不需要理会货架 -- 解耦

- 签到一次的过程：

  - 添加签到相关的参与次数表、活动sku表
  - 执行签到时，查看签到的sku表是否还有剩余库存；
    - 有则查看签到对应的次数编号，获取总次数、日次数、月次数内容

  - 记录活动下单流水：记录对应用户签到行为导致的总次数、日次数、月次数变化。
  - 修改活动次数账户：修改对应用户的次数、剩余次数数据

![img](./assets/Fk8-I3lPBhm5fN6PZpAGfMH5GO2--1759037327443-5.png)

解释：

- 抽奖活动表：仅仅与抽奖活动的总体信息相关
- 参与次数表：每种行为导致的总次数、日次数、月次数**变化**。（如：签到导致总次数、日次数、月次数均变化1次）
- 活动SKU表：每种行为表示为一个SKU，对应一条数据。如：签到->sku1、抽奖活动id、对应的次数编号、签到单独的库存、签到剩余的库存。
- 用户活动次数汇总表：每个用户对应一条数据，记录用户对于活动id的次数和剩余次数。
- 用户参与次数记录：记录用户每次下单的流水。一次下单/签到等对应一条数据，其中总次数、日次数、月次数分别说明该次记录涉及的变化值。

### 抽奖活动流水入库

总结：使用外部提供的唯一防重复id提供幂等性保障；链式验证过程可以使用责任链；同时更新多个数据库需使用事务操作。

【知识点】

- 幂等：防止一个请求执行多次；添加一个**外部透传的唯一id【外部生成的id，跟随请求一同传输，相同请求，id相同，故可以区分不同请求】**并作为唯一索引值，对于同一个请求，该id一致，从而确保不会多次添加同一个请求的内容。
- 责任链：
  - 一个节点接口（next、appendNext）、一个节点行为接口(action)
  - 一个节点抽象类，实现节点接口内容
  - 多个节点行为实现类，继承节点抽象类；实现每个节点的行为内容，并通过`Component`注解添加实现类到bean
  - 工厂组装
    - 责任链拼接：获取每个节点行为实现类的map，并将每个行为实现类使用appendNext连接；
    - 提供责任链到外部：返回拼接后的责任链给外部调用。

### 引入MQ处理活动SKU库存一致性

总结：使用RabbitMQ确保耗尽库存的最终一致性。

【知识点】

- 微服务：每一个子功能都作为一个系统，使用rpc socket通信。
- 趋势更新库存：延迟队列 + 定时任务

- RabbitMQ:用于库存消耗完之后更新数据库，保证最终一致性。
  - 定义消息模板：基础设施层定义消息模板（消息的字段和内容）
  - 发送消息API:基础设施定义发送消息api（publisher）
  - 创建消息并发送消息：领域模型创建消息并发布
  - 消费消息：触发层监听消息的发布，从而消费消息；调用基础设施层的dao来更新MySQL数据库。

功能流程

![img](./assets/FvvFGEWzmC6q7S_tMgxI3vbymMHJ.png)

1. 第一步；完成责任链的活动校验，时间、状态、库存。
2. 第二步；对库存的扣减，使用 decr + lock 锁的方式（兜底）进行处理。

组件介绍

![img](./assets/FkZZBAx3pr7XCQECTfDRcbrdv22c.png)

canal ，译为水道/管道/沟渠，主要用途是基于 MySQL 数据库增量日志解析，提供增量数据订阅和消费。

早期阿里巴巴因为杭州和美国双机房部署，存在跨机房同步的业务需求，实现方式主要是基于业务 trigger 获取增量变更。从 2010 年开始，业务逐步尝试数据库日志解析获取增量变更进行同步，由此衍生出了大量的数据库增量订阅和消费业务。

它的工作原理是，canal 模拟 MySQL slave 的交互协议，伪装自己为 MySQL slave ，向 MySQL master 发送dump 协议。在 MySQL master 收到 dump 请求，开始推送 binary log 给 slave (即 canal ) 这样 canal 再解析 binary log （binlog）进行配置分发，同步到 Elasticsearch 等系统中进行使用。

那么有了 canal 就可以把分库分表的数据同步到 Elasticsearch，提供汇总查询和聚合操作，也就不需要轮训每个分库分表数据了。

### 增强抽奖算法策略

总结：多种存储抽奖概率算法和查找方法

【知识点】

- 多种存储抽奖概率算法：
  - O(1):使用list存储每个数字，乱序后转为map【数据范围量小】
  - O(logn)：保存边界，并循环对比查找。【数据范围量大】

方案设计

![img](./assets/big-market-47-01.png)

如图，8个奖品概率。1个0.79、6个0.03，1个0.0003，总概率和不是1。对于这样的一个可设定不同范围值的抽奖，怎么做研发方案呢？怎么让做的这个方案可以支撑不同概率类型的大规模抽奖呢？

在实际生产场景中，运营的奖品配置概率有时候百分位或者千分位，也就是小数点后有几个0，但有时候也有需要配置到万分位或者百万分位，来降低大奖的奖品概率配置。

对于不同概率的抽奖配置，我们也有为它设计出不同的抽奖算法策略。让万分位以下的这类频繁配置的，走O(1)时间复杂度。而对于超过万分位的，可以考虑循环对比，但在循环对比的中，还要根据奖品的数量设定出不同的计算模型。如；O(n)、O(logn) 如图；

![img](./assets/big-market-47-03.png)

- 算法1；是O(1) 时间复杂度算法，在抽奖活动开启时，将奖品概率预热到本地(Guava)/Redis。如，10%的概率，可以是占了1~10的数字区间，对应奖品A。11~15 对应奖品B。那么在抽奖的时候，直接用生成的随机数通过对 map 进行 get 即可。

- 算法2；是O(n) ~ O(logn)算法，当奖品概率非常大的时候，达到几十万以上，我们就适合在本地或者 Redis 来初始化这些数据存到 Map 里了。那么这个时候就要把奖品概率，拆分为一个个有限定范围的格子区间。比如 1~7900代表一个奖品、7901~8200代表另外一个奖品，把这些数据存储到 `Map<Map<Integer,Integer>,Integer>` 在抽奖的时候通过产生的随机值来与这些范围区间依次进行对比。那么为了更好的优化抽奖算法，可以的分别对<=8的进行for循环、<=16的二分查找、>16的进行多线程计算。因为熟练很小开启多线程的资源也是一种消耗。

#### 业务述求

提供多种抽奖的装配算法和抽奖实现算法。
